1. Overview: the loop that never closed

The DMA signal engine runs a closed-loop correction: once per signal cycle (~280 µs) the Core-1 control point reads the latest AN3/AN5/AN6 measurement and adjusts the waveform. The controller enforces a hard measurement-age budget of one signal cycle, because a correction computed from stale feedback can push a power converter in the wrong direction.

The starting symptom: with the signal running and control in compute-only mode, the freshest available snapshot was ~1600 µs old against a 282 µs budget. The staleness gate rejected essentially every sample, so live control could never stay on. The controller math was fine — it simply never received data it was allowed to use.

This document walks through the three distinct problems that stacked up to that symptom, why each one was a problem, how each was solved, and ends with the measured evidence: the hardware acceptance test going from pass: false on every run to pass: true on every run, with the worst consumed-sample age dropping from ~1 ms to ~143 µs.

3. Problem 1: one frame per wake left backlog in the driver

The ADC runs in continuous (DMA) mode at 250 kS/s. The hardware fills a driver ring buffer with 12-sample frames (one frame ≈ 48 µs of signal). A Core-0 acquisition task wakes on each conversion-done interrupt, reads frame data, assembles AN3/AN5/AN6 triples, and publishes the newest one into a seqlock snapshot that the Core-1 control point reads.

What was wrong

The acquisition task read exactly one frame per wake-up, then yielded. That is fine as long as the task is scheduled once per frame — but Core 0 also runs the whole BLE stack, so the task was frequently scheduled in bursts: nothing for a while, then several pending notifications at once. Reading one frame per wake meant old frames sat in the driver while newer ones kept arriving. The published triple was systematically behind the newest available data, and the driver reported frame_drops ≈ 15 000 per two-second window.

Why it mattered

The control point only ever wants the newest measurement. Every frame of backlog between the newest converted sample and the published triple is pure, avoidable measurement age — and the budget is only ~6 frames wide in total.

The fix

Rework the read path into a per-frame reader plus a drain loop: on each wake, consume frames until the driver reports empty, fold them all into the triple accumulator, and publish once. The wake-up notification was switched to clear-on-take so a burst of pending notifications collapses into a single drain pass instead of one spin per frame.

Alongside the fix, two cadence-correlation counters were added: control_triggers (control-point reads) and publishes (valid triples published). These settled the key diagnostic question below.

What it proved

After the drain fix, supply outpaced demand ~4.6× (publishes: 26 021 vs control_triggers: 5 635) — yet stale and over-budget reads persisted. Conclusion: throughput was never the bottleneck. Something else was inflating the ages (Problem 2) and punching holes in the publish cadence (Problem 3).

4. Problem 2: the ISR timestamp ring lied under flush_pool

Measurement age is computed from the sample's conversion time, not its publish time, so each frame needs an honest timestamp. The original design captured one timestamp per frame in the conversion-done ISR, stored it in a small ring, and the acquisition task popped the oldest entry when it read a frame — assuming timestamps and frames pair one-to-one in FIFO order.

What was wrong

The driver runs with flags.flush_pool = 1: when its internal pool fills, it silently discards old frame data to keep the freshest samples. That is exactly the right policy for closed-loop control — but it breaks the pairing assumption. The ISR pushed a timestamp for every completed conversion, including frames the driver then threw away. The ring accumulated orphan timestamps belonging to no readable frame, so popping "the oldest" handed out a time from several frames ago.

Why it mattered

This bug was self-hiding. With the ring at its original depth of 2, the ISR constantly overwrote old entries (~15 000 frame_drops per window), which accidentally limited how far the pairing could drift — while also forcing occasional read-time fallbacks (ts_fallbacks > 0, itself a test failure). The decisive experiment: deepening the ring to 16 made every reported age jump to ~1.4 ms. The deeper ring did not add latency — it removed the accidental masking and exposed the orphan-timestamp accumulation. The ages the controller had been rejecting were partly fiction.

The fix

The per-frame ISR timestamp is fundamentally incompatible with flush_pool, so the ring was deleted outright. Frames are stamped at read time, with each sample inside the frame backdated by its position at the configured conversion rate. Because the reader wakes on the conversion notification and drains immediately, read time tracks the newest frame's completion; a genuine scheduling gap still surfaces honestly as an equally old snapshot downstream. The ISR shrank to a pure task-notify.

Result

frame_drops: 15 000 → 0 and ts_fallbacks → 0 (both by construction), and the worst consumed age fell from ~1.1 ms to ~0.9 ms. What remained was no longer a measurement artifact — it was a real scheduling gap (Problem 3).

5. Problem 3: the Core-0 BLE preemption tail

With Problems 1 and 2 fixed, the numbers were honest for the first time: supply was 4.6× demand, frame_drops and ts_fallbacks were zero — and yet ~0.3–0.5% of consumed samples were still up to ~1 ms old, and ~2% of control reads found no new sample at all.

What was wrong

The core-pinning layout is fixed by the system's real-time design: Core 1 is reserved for the signal engine, so the acquisition task, the BLE radio controller (priority ~23), and the Bluedroid host (~19–20) all share Core 0. When the host processes a notification batch it runs for up to ~1 ms without yielding to an IDLE+8 task. During that window no publish can happen, no matter how much ADC data is ready. Any control trigger landing inside the window reads a snapshot exactly as old as the gap.

Why it mattered

This tail cannot be fixed by buffering (depth prevents data loss, not staleness) or by more sample rate (supply was already 4.6× demand). The only producer-side lever left was task priority — and the experiment showed that lever is welded shut:

Acquisition priorityTail (over-budget count)Side effect
IDLE+8 (baseline)9–23 per run—
IDLE+12 (below Bluedroid host)17–21 — no changenone, but useless
IDLE+21 (above Bluedroid host)unmeasurablestarved the Core-0 console/UART; harness lost contact

Below the host, the host still wins the core; above the host, the rest of Core 0 starves. There is no safe priority window. The residual tail is an architectural floor of having the measurement producer on the same core as the BLE stack — which forced the real question: why is the producer on Core 0 at all?

6. The solution: read at the point of need, on Core 1

The decisive observation: the project rule "interrupts are disabled on Core 1 during signal generation" applies to the CPU bit-bang engine. The DMA engine's control task is different — hardware DMA drives the pins while the task simply blocks on a notification, so at its control point interrupts are on and calling the ADC driver is legal. That means the consumer can fetch its own measurement.

The architecture change

Instead of a Core-0 producer racing the BLE stack to publish snapshots that Core 1 then reads, Core 1 drains the ADC ring buffer itself, inline at the control point, on every control trigger:

  • Driver stays on Core 0. The ADC continuous driver is started from a Core-0 context so its DMA-EOF interrupt stays pinned to Core 0, filling the ring buffer in hardware regardless of what either CPU is doing.
  • Core 1 reads at the moment of need. At each trigger it drains all pending frames (bounded at 8 — the watchdog is off on Core 1, so the loop must be provably finite), assembles the newest triple, and publishes it to the same seqlock the telemetry path already reads.
  • Read is decoupled from control. The drain runs on every trigger; g_control_enabled only gates whether a correction is applied. Debug reads therefore work with control off, and telemetry stays live whenever the signal runs.
  • The correction path needed zero changes. signal_control_update_corrections still reads the seqlock — which Core 1 itself just wrote in the same task, so the read is coherent, contention-free, and its existing sequence-repeat check provides stale detection for free.

Why this solves each problem

ProblemHow the inline drain removes it
Backlog between newest sample and published triple The consumer drains to the newest frame at the moment it needs it; there is no intermediate publish cadence to lag behind.
Timestamp inflation Read-time stamping is exact here: the drain happens synchronously with consumption, so age ≈ one frame (48 µs) + drain time, by construction.
BLE preemption tail The measurement path no longer contains any Core-0 task. Bluedroid bursts can delay telemetry housekeeping, but they cannot age the sample the controller consumes.
Seqlock contention Writer and reader are now the same task while the DMA engine runs; miss_contention is structurally impossible, not just rare.

The single-reader hand-off

The ADC driver's ring buffer tolerates exactly one drainer. Ownership is a token with a Dekker-style busy handshake: the Core-0 acquisition task grants it only after the driver is started and reclaims it only after any in-flight Core-1 drain acknowledges completion. When the DMA engine is not active (CPU engine, or signal stopped), Core 0 drains exactly as before — the CPU engine and stopped-state telemetry paths are untouched.

Guard rails

  • drain_max_us metric: the drain runs in the maintenance window of the real-time loop, so its worst-case duration is tracked per run. Measured: flat ~137–140 µs worst case, well inside the window.
  • Sample-rate changes are deferred while Core 1 holds the token (restarting the driver under an active drain would race); they apply at the next signal start.
  • Bounded drain loop + no allocation + no blocking calls on the Core-1 path.

8. Open items and caveats

  • Stop/reclaim validation (pending). The signal auto-starts at boot, so the UART harness only exercises the running path. Validate via the web UI: Connect → Start → Stop → confirm the Readings panel still updates while stopped (Core-0 reclaim + continuous fallback).
  • Raw AN3/AN5/AN6 read 0. Independent of the timing work: raw ADC codes are zero (calibrated to the 0.1 V floor). Check sense-line wiring/energisation, channel mapping, and attenuation before trusting live corrections.
  • Live-control smoke test. All evidence above is compute-only mode. Once the sense inputs read real voltages, repeat the loop with control LIVE and confirm consecutive_misses stays below the auto-disable threshold.
  • Sample-rate changes defer to next start while the DMA engine runs (deliberate: restarting the driver under an active Core-1 drain would race). The analog config sweep tool is likewise less meaningful while the signal is running.
  • CPU engine unchanged. The inline drain is scoped to the DMA engine; the CPU bit-bang engine still consumes Core-0 published snapshots and inherits the old limitations. If it ever needs closed-loop freshness, its read must go in its maintenance window (interrupts on), never the interrupt-disabled generation block.
