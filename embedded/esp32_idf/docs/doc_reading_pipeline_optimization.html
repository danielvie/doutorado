1. Goal, method, headline result

Goal: measure how long each step of the analog reading pipeline takes — driver read, parsing, triple assembly, calibration, transport (seqlock publish + snapshot read), correction math — then optimize only where the data says it matters.

Method: eight cycle-count probes (nanosecond resolution, two counter reads per stage, negligible overhead) inserted along the Core-1 control path, reported per stage as count / average / max through the existing UART hardware-in-the-loop harness (task uart:control-latency). Every number below is from the real board with the signal running and control in compute mode.

Three planned optimizations were implemented — and the probes caught a fourth, unplanned problem mid-flight (a flash-cache regression) whose fix ended up delivering the single largest improvement. That detour is documented honestly below; it is the most instructive part of the exercise.

2. Probe methodology and the baseline breakdown

The probes bracket each stage with esp_cpu_get_cycle_count() reads and accumulate count / sum / max per stage in relaxed atomics (single writer: the Core-1 control path). Stages, in pipeline order:

  1. adc_read — each adc_continuous_read() driver call, including the final empty call that terminates a drain
  2. parse — decoding 12 samples per frame, timestamp backdating, channel-queue push
  3. assemble — combining the per-channel queues into complete triples
  4. calib — LUT calibration of the published triple (3 lookups)
  5. publish — seqlock write + compatibility globals (transport, write side)
  6. snapshot — control-point seqlock read + validity gates (transport, read side)
  7. math — error computation, gain multiply, conditioning, duration corrections
  8. render — bitstream re-render (only when a correction is applied; ~80–87 µs, not part of the per-trigger reading cost in compute mode)

What the baseline probe run showed

Two immediate negative results, both valuable:

  • Calibration is free (766 ns): the LUT design is already optimal; nothing to do there.
  • The driver read is cheap (2.8 µs/call): the ESP-IDF ringbuffer path is not the bottleneck, so no driver surgery is warranted.

3. The three planned optimizations

Optimization 1 — parse: one divide per frame, one atomic commit per frame

Why it was slow. The parse loop ran, per sample (12 per frame):

  • a 64-bit division for timestamp backdating ((idx × 1 000 000) / sample_hz) — Xtensa LX6 has no 64-bit divide instruction, so each is a software-library call costing hundreds of cycles;
  • four atomic read-modify-writes for statistics (samples-read, per-channel count, last-raw, and occasionally rejected) — each an S32C1I compare-and-swap loop with memory barriers.

The fix. Conversions are evenly spaced, so the backdate is arithmetic: compute the 4 µs step once per frame and accumulate additively. Statistics accumulate in stack locals and commit with a handful of atomics per frame instead of ~48 per frame's worth of samples.

Show code: cpp
// before: per sample
          ts = frame_ts - ((uint64_t)(n-1-i) * 1000000ULL) / sample_hz;  // 64-bit soft-div
          s_samples_read.fetch_add(1, acq_rel);                          // x4 atomics
          
          // after: per frame
          uint32_t step_us = 1000000U / sample_hz;    // once
          ...
          for (...; sample_ts_us += step_us) { ... }  // additive
          s_samples_read.fetch_add(local_read, relaxed);  // one commit

Result: 15.3 → 7.3 µs per frame (2.1×), max 45 → 11 µs.

Optimization 2 — assemble: stop paying for triples nobody reads

Why it was slow. The assembler popped every complete triple one by one — each pop with an esp_timer_get_time() call and rate-window atomics — and then kept only the final (newest) one. With ~5–8 triples per trigger, that is 4–7 fully-processed triples discarded per cycle.

The fix. Compute how many complete triples exist (min of the three queue counts), advance the queue heads past the older ones in O(1), pop only the newest, and record the skipped count in a single bulk rate update.

Result: 21.7 → 3.1 µs (7×), max 50 → 8 µs. (Interim measurement showed 9.1 µs; the rest of the gain arrived with the cache fix in the next session — assemble was also paying flash-cache penalties.)

Optimization 3 — publish: single-writer seqlock protocol

Why attempted. The seqlock writer used two fetch_add(acq_rel) RMW retry loops for the sequence counter. Since the reader-token hand-off guarantees a single publisher at any time, the canonical store/fence/store protocol suffices — plain stores instead of CAS loops.

Result: no measurable change (4.7 → 4.8 µs). Reported honestly: the publish stage is dominated by the rate-window bookkeeping and compatibility-global stores, not the sequence counter. The change is kept — it is simpler, provably correct for the single-writer case, and removes two retry loops from the hot path — but it bought no time. The probe prevented mistaking a tidy refactor for an optimization.

4. The unplanned find: flash-cache eviction, fixed with IRAM

After flashing optimizations 1–3, the target stages improved as predicted — but two stages that were not touched at all got consistently worse: math went 7.3 → 20.0 µs and snapshot 3.6 → 7.5 µs, reproducible across every run. Code that nobody edited slowed down 2.7×.

Diagnosis: flash-cache eviction

On the ESP32, ordinary code executes from external flash through a small instruction cache. The optimization rework changed the size and layout of the drain-path code that runs immediately before the math each cycle — and the new layout evicted the math/snapshot cache lines on every pass. Each control trigger then re-fetched that code from flash (~40 µs-class SPI reads amortized), turning a 7 µs computation into a 20 µs one. The stage cost was never the instructions; it was where the instructions lived.

Fix: pin the hot control path in IRAM

signal_control_update_corrections (which inlines the conditioning and correction helpers), analog_read_control_snapshot, and the seqlock reader were marked IRAM_ATTR, placing them in internal RAM where cache pressure cannot touch them.

Two lessons worth keeping

  • On flash-XIP microcontrollers, per-stage probes are not optional. A whole-path timer (drain_max_us) would have shown a net improvement and hidden the 2.7× math regression entirely. Only the per-stage breakdown exposed that unrelated code had slowed down — the signature of a cache effect rather than an algorithmic one.
  • Real-time code paths belong in IRAM as a matter of policy, not tuning. Any future edit anywhere in the firmware can reshuffle flash layout and silently re-tax a flash-resident control path. The hot Core-1 path is now layout-immune.

5. Final results and remaining opportunities

Final verification: three consecutive hardware runs after all changes, every run pass: true, probe values reproducible to the tenth of a microsecond.

The most meaningful line is the first: the worst consumed-sample age is not only 4× smaller, it is bit-identical across runs. The pipeline's timing is now dominated by deterministic work, not by scheduling or cache accidents — exactly the property a control loop wants.

Remaining opportunities (in value order)

  1. render, ~80 µs — irrelevant in compute mode but paid on every corrected cycle in LIVE mode, where it would instantly be the largest block. An incremental re-render (only steps whose duration changed) is the next big lever before live-control tuning.
  2. parse, 13.5 µs — still the largest reading stage (~580 ns per sample: decode + queue push). Structurally shrinkable, but note the synergy below before spending effort here.
  3. Deterministic sampling (see the sampling-vs-switching study) would delete adc_read + parse + assemble entirely (~25 µs) and replace them with three oneshot conversions — solving the switching-noise problem and most of the remaining pipeline cost in one move. If that plan proceeds, do not micro-optimize parse first.
