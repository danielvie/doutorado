1. Overview: why measure the phase at all

This document analyses the first results of the sampling-phase instrumentation — step 3 of the phased plan set out in the sampling-vs-switching study. The study predicted that because the ADC free-runs against the switching pattern (independent clock dividers), the sampling phase does not scatter randomly: it walks slowly and dwells at nearly fixed positions for many consecutive cycles, including positions inside the post-edge disturbance bands. That prediction was made from first principles; this step measures it on the running system, producing the "before" evidence against which deterministic placement (Scenario B) will later be judged.

The measured quantity is deliberately cheap and behaviour-preserving: for each triple the Core-1 control point consumes, record read_cycles − s_trigger_cycles — the offset, in CPU cycles converted to µs, between the instant the newest ADC frame was read and the pass's trigger anchor (captured sub-µs by the DMA trigger ISR at a fixed waveform position). Nothing about the pipeline's behaviour changes; only a counter, min/max, and a 32-bin histogram are added.

What this offset is — and is not. It anchors the read instant, not the conversion instant: the newest frame finished converting anywhere in the preceding 0–48 µs (one DMA frame), which is exactly the uncertainty that ruled out Scenario A. The offset is therefore useless for validating any individual sample. What it can show is the structure of the timing relationship between the free-running ADC delivery and the trigger cadence: if the phase walked uniformly, the histogram would be flat; if it dwells, the histogram concentrates into discrete modes. That structural question is the one step 3 was designed to answer.

2. Implementation: four small additions

Four small changes, all mirroring existing patterns (the stage probes and drain_max_us metric):

  1. Phase anchor getter. The trigger ISR already stamps s_trigger_cycles; a one-line getter exposes it to the analog helper.
  2. Per-frame read stamp in the Core-1 drain. The control-point drain captures the cycle count after each successful frame read; the last capture belongs to the frame that completed the consumed (newest) triple.
  3. Stats: count / min / max / histogram. Single writer (the Core-1 drain during a DMA run), relaxed atomics, 32 bins × 4 µs with the last bin absorbing overflow. Reset at control-session prepare alongside the probes.
  4. UART exposure. A "phase" block in the agent control-latency JSON.
Show code: cpp
// signal_engine_dma.cpp — expose the ISR's phase anchor
          uint32_t signal_dma_trigger_cycles(void) {
              return s_trigger_cycles;
          }
          
          // helper_analog.cpp — inside analog_control_drain_publish()
          uint32_t last_read_cycles = 0;
          for (int i = 0; i < ANALOG_CONTROL_DRAIN_MAX_FRAMES; ++i) {
              if (analog_continuous_read_frame(&s_control_acc, sample_hz) != 1) {
                  break;
              }
              // Read instant of the newest frame so far; the last capture belongs
              // to the frame that completed the consumed (newest) triple.
              last_read_cycles = esp_cpu_get_cycle_count();
              consumed = true;
          }
          if (consumed) {
              analog_publish_queued_triples(&s_control_acc);
              uint32_t trigger_cycles = signal_dma_trigger_cycles();
              if (trigger_cycles != 0) {
                  analog_phase_record((last_read_cycles - trigger_cycles) /
                                      esp_rom_get_cpu_ticks_per_us());
              }
          }

The drain runs on the trigger notification, strictly after the ISR stamped the anchor, so the subtraction is same-pass and non-negative; unsigned wrap-around handles counter overflow. Cost inside the maintenance window: one CCOUNT read per frame plus a handful of relaxed atomic stores — well under a microsecond.

3. Results: a razor-sharp trimodal histogram

Test loop: task flash, then task uart:control-latency (COM3, alpha = 0.5 dataset, DMA engine, dry-run control). Two independent runs, each ≈4 k consumed triples over the measurement window:

The distribution is trimodal and razor-sharp: 3824 of 4072 samples (93.9%) fall in just three 4-µs bins, and 99.4% within those bins plus their immediate neighbours. The three modes sit at 28–32, 40–44, and 52–56 µs — spaced exactly 12 µs apart, the ADC triple period. The second run reproduces the same three modes with slightly different weights, which is precisely what a slowly walking phase should produce: the mode weights shift between runs as the beat drifts, but the mode positions are pinned by the conversion cadence.

4. Analysis: dwell confirmed, Scenario A's grave measured

Three conclusions follow from the shape of the histogram:

1. The dwell prediction is confirmed

A free-running phase that scattered independently each cycle would fill the 25–70 µs span roughly uniformly. Instead the offset occupies discrete modes locked to the 12 µs triple cadence, with the gaps between them essentially empty. The timing relationship between ADC delivery and the switching pattern is quantised and persistent — when the newest sample's phase is bad, it stays bad across many consecutive control cycles before the beat walks it onward. This is the burst-corruption mechanism the study warned about, now observed directly on the running system rather than argued from clock arithmetic.

2. The uncertainty that killed Scenario A is also visible

The full spread (25–71 µs across both runs, ≈46 µs) matches the study's ±~24 µs read-time-stamp uncertainty almost exactly — one DMA frame (48 µs) of ignorance about when the consumed triple actually converted. The same plot that confirms the dwell also demonstrates why validate-and-reject cannot work: a ~46 µs-wide uncertainty cannot adjudicate a ~5 µs guard band.

One caveat on interpretation: the recorded offset anchors the read instant of the newest frame, so mode positions also fold in the task wake latency and per-frame read time. The 12 µs mode spacing and the dwell behaviour are properties of the underlying conversion cadence and survive that folding; the absolute mode positions should not be read as conversion phases. Deterministic placement (Scenario B) does not need them to be — it replaces this whole distribution with a single chosen instant.

5. Next steps

With the "before" evidence captured, the plan's remaining steps are unchanged:

  1. Fix the sense inputs (hardware, blocking). AN3/AN5/AN6 still read raw 0 (raw_zero: true); until real voltages arrive, no disturbance is observable and signal-quality claims cannot be tested.
  2. Measure the real guard band on the converter with a scope; replace the assumed 5 µs. Every downstream design number depends on it.
  3. Implement Scenario B (deterministic placement): oneshot owned by Core 1 behind the existing reader-token hand-off, sample at the dataset-derived quiet-window midpoint, overrun self-check invalidating preempted triples, plus sample_window_us / placement_jitter_max metrics. Measure the actual oneshot conversion-train duration early — the study assumed ~4 µs per conversion; if it is closer to 10 µs the ~18 µs quiet-window rejection threshold must be recomputed.
  4. Validate: placement jitter ≤ 2 µs, overrun invalidations ≈ 0, age_used_max_us unchanged or better, pass green — and this document's histogram collapsing from three walking modes to a single pinned one is the headline before/after picture.
