1. Simulation: before the same cycle

β scales the requested switching-time offsets. It is not a waiting time. The simulation computes one β from the cycle-start state, then uses that schedule for the entire cycle.

No β recalculation occurs at the intermediate edges. MATLAB takes real CPU time, but the simulation adds zero computation delay to the signal. Internal edges move earlier or later; the modeled cycle endpoints stay fixed.

2. ESP32 DMA: compute while the signal continues

The default ESP32 engine uses I2S/DMA to play a prepared waveform. At an eligible control trigger, the CPU reads a snapshot, computes −Ke and β, then prepares the next buffer. Playback does not wait for this calculation.

The trigger lead is configured as 120 µs, capped at half a pass. This is not β's execution time. A pass may contain several repeated cycles.

Late commits can postpone application. The pending-flip logic also skips an intervening live-control calculation, so the current code does not guarantee a fresh β every cycle. The diagram shows the intended application of one accepted update.

3. CPU engine: finish before the next edge

The alternative CPU engine returns from playback just after entering the last mode. While that mode remains asserted, it performs bookkeeping and the next control calculation, including β.

If the work fits, absolute timing keeps the edge on schedule. If it overruns, the edge can be late. Dead time, edge overhead, and interrupts further reduce the usable window. The article's minimum dwell is not a guaranteed computation budget.

Bottom line: simulation ignores computation delay; DMA overlaps computation with playback; CPU playback can directly suffer a late edge.
